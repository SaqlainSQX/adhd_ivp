# P: integrity checks under Python interpreter modes

Registered8 November2026 after O. This is a bounded engineering reliability
check, not a new benchmark experiment. Preserve the N/O baseline, scientific
results and all previous evidence. No GPU, oracle, model or download work.

In new source-only staged trees, test the existing aggregate builder under
both normal isolated/no-site Python and optimized isolated/no-site Python
(`-I -S` versus `-I -S -O`). Each mode has three fixed cases: intact inputs,
missing UCO aggregate source, and a controlled numerical change to the pinned
UCO primary full-weight RMSE. Use only copies; never alter the live page's source
data. Record commands, source commit and hashes before these outcomes.

Check whether altered data is rejected before an export is generated in every
mode, and whether intact outputs exactly match the accepted artifacts after
newline normalization. This specifically checks reliance on Python assertions;
it is not an adversarial security audit or a claim that users cannot edit code
and manifests together. Do not infer a new statistical finding from these tests.

If an integrity condition is bypassed, preserve the demonstrated failure and
implement an additive verified builder/entry point using explicit exceptions
for input/provenance validation. Do not rewrite the immutable N implementation
or mutate its evidence manifest. Register the repair and new output version
before rerunning the same six cases. Verify that repaired intact JSON/JS outputs
are unchanged and the numerical tamper and missing-file controls produce no
export. Avoid adding unrelated dependency or schema changes.

Save a concise result and update the teammate instructions only after evidence
is concrete. Existing services stay running; the in-app download helpers remain
excluded because of their known capture timeout. Continue the standing program
without turning this into an endless parameter or browser retry loop.
